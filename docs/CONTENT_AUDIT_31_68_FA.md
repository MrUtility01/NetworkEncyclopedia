**تاریخ:** ۱۷ اکتبر ۲۰۲۶  
**منبع بررسی:** مخزن GitHub و فایل‌های راهنمای پروژه.  
**وضعیت اجرا:** JSONها از نظر parse، ساختار درس‌ها، UID یکتا در هر بسته، حداقل طول محتوا، تعداد سؤال‌ها و جدایی answer key در زمان تولید کنترل شدند. دیتابیس عملی `server/data/encyclopedia.db` در GitHub وجود ندارد؛ بنابراین نمی‌توان صحت تعداد و طول رکوردهای ذخیره‌شده در اجرای واقعی Windows را بدون اجرای اسکریپت روی همان دستگاه تأیید کرد. ## نتیجهٔ اجرایی

برای فصل‌های **۳۱، ۳۲، ۳۳ و ۴۰ تا ۶۳**، ۱۲ بستهٔ حرفه‌ای canonical در `tools/packs/professional_chapters/` آماده شده و همراه این commit افزوده می‌شوند:

- **۳۸۳ topic** از اسکلت رسمی محتوای فصل‌ها.
- **۱٬۹۱۵ درس**؛ پنج سطح L0 تا L4 برای هر topic.
- **۳٬۸۳۰ سؤال**؛ دو سؤال برای هر درس.
- طول `full_content` تمام درس‌های تولیدشده دست‌کم **۴٬۹۹۳ نویسه** است.
- هر درس دارای `uid`، نمونه فرمان‌ها، آزمایشگاه مجاز، عیب‌یابی Symptom → Scope → Evidence → Fix → Verify، نکات امنیتی، rollback و معیار پذیرش است.
- پاسخ‌ها فقط در `meta.assessment.answer_key` قرار دارند؛ گزینه‌ها فیلد `correct` ندارند.
- `source_status=review_required` حفظ شده تا فرمان‌های وابسته به محصول/نسخه/ماژول/tenant در محیط مقصد بازبینی شوند.

## مسیر ادغام و آزمون پس از pull

### Windows / SQLite

از ریشهٔ مخزن، روی دیتابیس همان برنامه اجرا شود:

```bash
python tools/audit_content.py --db server/data/encyclopedia.db --json docs/content_audit_local.json
```

سپس برای seed و اعمال بسته‌ها از مسیرهای ثبت‌شده در پروژه استفاده کنید. تعداد رکوردهای unmatched یا محتواهای skip شده باید بررسی شود؛ اجرای موفق دستور بدون بررسی این شمارش‌ها کافی نیست.

### Android

`scripts/merge_content_packs_into_android.py` بسته‌های `tools/packs/**/*.json` را در asset دانشنامه merge می‌کند. پس از pull باید workflow ساخت APK اجرا و متن چند درس نمونه از فصل‌های ۳۱، ۳۲، ۳۳، ۴۰، ۴۲، ۵۰، ۵۹، ۶۰ و ۶۳ همراه با نمایش آزمون و پاسخ‌نامه بررسی شود. این گزارش، build سبز یا نصب APK را ادعا نمی‌کند.

## تعریف «غنی» در این گزارش

۱. متن هر درس >= ۲٬۰۰۰ نویسه و دارای مفهوم، معماری و روند اجرایی باشد.  
۲. نمونهٔ فرمان با قید محیط، نسخه و شواهد مورد انتظار داشته باشد.  
۳. Lab دارای baseline، مسیر موفق/ناموفق، معیار پذیرش و cleanup باشد.  
۴. عیب‌یابی بر اساس evidence انجام شود، نه حدس یا reset کور.  
۵. کنترل امنیت، rollback، معیار پایان و واژه‌نامه درج شود.  
۶. `uid` پایدار و سؤال/پاسخ جدا حفظ شود.  
۷. آزمون runtime به‌عنوان «انجام شده» ثبت نشود مگر واقعاً اجرا و نتیجه آن مشاهده شده باشد.

**جمع‌بندی صادقانه:** محتوای canonical فصل‌های ۳۱–۳۳ و ۴۰–۶۳ به صورت بسته‌های حرفه‌ای به مخزن اضافه می‌شود و منطق Windows seed برای این بسته‌ها اصلاح می‌شود. فصل‌های ۳۴–۳۹ و ۶۴–۶۸ دارای دارایی‌های قبلی هستند. ممیزی واقعی SQLite و build/install نهایی Android همچنان نیازمند اجرا در محیط مقصد است.
