## مسیر ادغام و آزمون پس از pull

### Windows / SQLite

از ریشهٔ مخزن، روی دیتابیس همان برنامه اجرا شود:

```bash
python tools/audit_content.py --db server/data/encyclopedia.db --json docs/content_audit_local.json
```

سپس برای seed و اعمال بسته‌ها از مسیرهای ثبت‌شده در پروژه استفاده کنید. تعداد رکوردهای unmatched یا محتواهای skip شده باید بررسی شود؛ اجرای موفق دستور بدون بررسی این شمارش‌ها کافی نیست.

### Android

`scripts/merge_content_packs_into_android.py` بسته‌های `tools/packs/**/*.json` را در asset دانشنامه merge می‌کند. پس از pull باید workflow ساخت APK اجرا و متن چند درس نمونه از فصل‌های ۳۱، ۳۲، ۳۳، ۴۰، ۴۲، ۵۰، ۵۹، ۶۰ و ۶۳ همراه با نمایش آزمون و پاسخ‌نامه بررسی شود. این گزارش، build سبز یا نصب APK را ادعا نمی‌کند.

## تعریف «غنی» در این گزارش

۱. متن هر درس >= ۲٬۰۰۰ نویسه و دارای مفهوم، معماری و روند اجرایی باشد.  
۲. نمونهٔ فرمان با قید محیط، نسخه و شواهد مورد انتظار داشته باشد.  
۳. Lab دارای baseline، مسیر موفق/ناموفق، معیار پذیرش و cleanup باشد.  
۴. عیب‌یابی بر اساس evidence انجام شود، نه حدس یا reset کور.  
۵. کنترل امنیت، rollback، معیار پایان و واژه‌نامه درج شود.  
۶. `uid` پایدار و سؤال/پاسخ جدا حفظ شود.  
۷. آزمون runtime به‌عنوان «انجام شده» ثبت نشود مگر واقعاً اجرا و نتیجه آن مشاهده شده باشد.

**جمع‌بندی صادقانه:** محتوای canonical فصل‌های ۳۱–۳۳ و ۴۰–۶۳ به صورت بسته‌های حرفه‌ای به مخزن اضافه می‌شود و منطق Windows seed برای این بسته‌ها اصلاح می‌شود. فصل‌های ۳۴–۳۹ و ۶۴–۶۸ دارای دارایی‌های قبلی هستند. ممیزی واقعی SQLite و build/install نهایی Android همچنان نیازمند اجرا در محیط مقصد است.

## الحاقیهٔ مرحلهٔ بعد — بررسی مسیر واقعی بارگذاری (۱۷ اکتبر ۲۰۲۶)

این الحاقیه وضعیت کد شاخهٔ main را از روی درخت فایل‌های GitHub ثبت می‌کند؛ **این نتیجه معادل اجرای برنامه یا ممیزی دیتابیس محلی نیست**.

### یافته‌های مهم

- بسته‌های JSON حرفه‌ای فصل‌های ۳۱–۳۳ و ۴۰–۶۳ در مخزن موجودند؛ بسته‌های فصل‌های ۳۴–۳۹ نیز در مسیر tools/packs/ وجود دارند.
- پوشه‌های عددی tools/chapters/1 تا tools/chapters/68 در درخت شاخهٔ main مشاهده نشدند؛ ساختار پوشه‌ای درخواستی هنوز تکمیل‌شده محسوب نمی‌شود.
- بارگذار قبلی درس‌های هم‌عنوان را بدون محدودکردن فصل جست‌وجو می‌کرد. این خطر وجود داشت که محتوای یک بسته روی درس هم‌نام فصل دیگری نوشته شود. در شاخهٔ ممیزی، تطبیق درس با chapter_order محدود می‌شود و نسخهٔ محتوایی برای بسته‌های حرفه‌ای ۳۱–۶۳ تغییر می‌کند تا دوباره اعمال شوند.
- بارگذار نتیجهٔ هر بسته را با matched / updated / missing ثبت می‌کند. اگر تعدادها مطابق انتظار نباشد، نشانگر نسخهٔ جدید ثبت نمی‌شود؛ بنابراین وجود فایل JSON به‌تنهایی به معنی ادغام موفق در SQLite نیست.

### وضعیت فعلی

| دامنه | وضعیت |
|---|---|
| بسته‌های ۳۱–۳۳ | موجود در مخزن؛ اجرای محلی و بررسی نتیجهٔ تطبیق لازم است |
| بسته‌های ۳۴–۳۹ | موجود در مخزن؛ اجرای محلی و بررسی نتیجهٔ تطبیق لازم است |
| بسته‌های ۴۰–۶۳ | موجود در مخزن؛ بارگذاری نسخه‌دار و تطبیق فصل‌محور در شاخهٔ ممیزی اصلاح می‌شود |
| فصل‌های ۶۴–۶۸ | دارایی‌های قبلی وجود دارند؛ مسیرهای اختصاصی Git/امنیت/OSPF-BGP/VPN/فرمان‌ها باید جداگانه با دیتابیس و Android تطبیق داده شوند |
| پوشه‌های tools/chapters/1..68 | در main دیده نشدند؛ انجام‌شده محسوب نمی‌شوند |
| دیتابیس Windows و APK | در این مرحله اجرا/نصب نشده‌اند؛ نتیجهٔ runtime ادعا نمی‌شود |

پس از دریافت شاخه، این دو ممیزی را اجرا کنید:

```bash
python tools/audit_content_packs.py --root . --json docs/content_audit_packs_local.json
python tools/audit_content.py --db server/data/encyclopedia.db --json docs/content_audit_local.json
```

گزارش اول JSONهای منبع را می‌سنجد؛ گزارش دوم رکوردهای واقعاً ذخیره‌شده در SQLite را می‌سنجد. هر دو باید بررسی شوند، پیش از آن‌که غنی‌سازی کامل اعلام شود.


### نتیجهٔ اولین اجرای CI روی شاخهٔ ممیزی

اولین اجرای خودکار بررسی منبع، compile پایتون را با موفقیت گذراند اما ۵ فایل قدیمی با JSON نامعتبر پیدا کرد: `rich_deep_pack_v11.json`، `rich_deep_pack_v17.json`، `rich_deep_pack_v19.json`، `rich_deep_pack_v21.json` و `real_lessons_core_pack.json`. در مرحلهٔ اصلاح، فقط newline/control character و escapeهای نامعتبر داخل رشته‌ها اصلاح شدند؛ هیچ رکوردی حذف نشد و محتوای معنایی بازنویسی نشد. هر پنج فایل پس از اصلاح با JSON.parse اعتبارسنجی شدند. اجرای CI بعدی باید دوباره این نتیجه را تأیید کند.

همچنین فرمان‌نامه‌ها از schema درس معمولی استفاده نمی‌کنند؛ ممیزی برای آن‌ها فیلدهای `command` و `usage` را هم محتوای معتبر حساب می‌کند. حالت پیش‌فرض ممیزی هشدار می‌دهد اما اجازه می‌دهد build ادامه یابد؛ با `--strict` وجود JSON نامعتبر باعث خروج غیرصفر می‌شود. این تغییر، خطاهای legacy را پنهان یا رفع‌شده اعلام نمی‌کند.
